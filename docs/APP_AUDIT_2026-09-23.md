## Fixed

1. **Mood invitations missing from Messages.** The server already persisted invitations and Android already fetched them, but only Now rendered them. Messages now reuses the invitation row, shows mood/activity and the host's invitation text, opens the existing Moment room, and supports dismissal. The Chats badge includes pending invitations. Inbox entry and polling refresh invitations without requiring a visit to Now; incoming `moment-invite` push events also refresh the cache.
2. **False success when telling selected people.** `TellPeopleSheet` discarded every invitation result and closed. It now keeps failed recipients selected, reports the failure, and retries only those recipients.
3. **Invitation cache lifecycle.** Invitation reads lacked the account check used by ordinary Moment reads. Reads now serialize with the existing repository mutex, discard responses after account changes, clear on logout, filter expired invitations, and refresh after audience changes.
4. **Inviting someone who cannot enter.** An accepted connection outside a CONTACTS-only audience could receive a success response and notification while the inbox and room rejected them. Sending now checks the recipient against the existing visibility rules before recording or notifying. Audience rules were not widened.
5. **Room action placement.** “Do something together” now lives in the existing header menu beside People/Invite/Leave or End. Its bottom button was removed; the existing activity sheet and actions are reused.
6. **Ending a shared Moment / keeping memories returned HTTP 500.** Three dynamically generated INSERT statements in `MomentsService` omitted the `$` prefix for SQL parameters. This broke keepsake audience creation, offer creation, and saving. Corrected all three; the existing keepsake integration suite covers the operations.
7. **Stale sealed-message integration expectation.** The Phase 3 test expected unreadable messages to disappear, contradicting Claude's later `roomMessages` implementation and unit tests. The integration assertion now requires a placeholder with no body or envelope, preserving the established behavior without exposing another device's ciphertext.

## Remaining findings

- **P1: Room closure is not atomic or retryable.** `end()` and `sweep()` mark the Moment terminal before `closeRoom()` finishes database/Redis cleanup. An exception can leave a terminal Moment with stale room data; later sweeps only select ACTIVE rows. The concrete malformed-SQL trigger above is fixed, but transaction/retry behavior remains a separate reliability issue.
- **P2: Notification settings are a dead row.** `YouScreen` still displays “Notifications — Coming soon” although Firebase push and reminder notifications are implemented. Users cannot reach notification controls from that row.
- **P2: Ending a Moment hides request failures.** `MomentRoomScreen` calls `room.markClosed()` after `session.moments.end()` without checking its `Result`. A failed request can therefore show the ending locally while the server still considers the Moment active. This is separate from the corrected keepsake SQL failure.
- **P2: Appearance choices are inconsistent.** `ViroTheme` selects a light Material color scheme, while consumer screens use static navy/white `ViroColors` values. Light mode therefore does not consistently change the app's appearance. This also appears in the previous Phase 3 report.
- **P2: Verification documentation is stale.** `COMPLETION_CHECKLIST.md` says Android FCM receiving/token registration is absent, although the receiver exists and is registered in the manifest. The Phase 3 report's no-placeholder description predates the later message-retention change.
- **Rive asset limitation already diagnosed by Claude.** Current code selects animation names from the file and avoids the unusable state machine. The asset's state machine remains broken; this audit preserved the existing animation/tap handling. Native rendering and the original TECNO crash cannot be certified by JVM tests.
- **Billing remains a preview.** The subscription service activates a selected plan without a payment-provider flow, consistent with the existing checklist's explicitly deferred billing scope. It is not evidence of paid billing being complete.
